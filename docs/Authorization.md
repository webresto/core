# Авторизация: как это работает

Справочник для тех, кто пишет клиент. Обоснования решений — в
`.ai-notes/auth/design2.md` и `.ai-notes/auth/extend_user_account.md`.

---

## 1. Один цикл на всё

Вход по телефону, вход через мессенджер, привязка второго способа из кабинета,
подтверждение удаления аккаунта — это **одна и та же попытка** (`AuthAttempt`) и один
и тот же цикл. Клиент реализует его один раз:

```
authStart(purpose, method?, login?) → { id, step }
  ↓ поллинг authStatus(id) → { status, step }      ← экран = функция этого ответа
  ↓ authSubmit(id, step.id, input)                 ← телефон или код
done → ticket → authExchange(ticket) → JWT
                либо ticket передаётся в защищаемую мутацию
```

Шесть операций: `authMethods`, `authStart`, `authStatus`, `authSubmit`, `authSwitch`,
`authResend`. Любой новый способ входа — новый **тип шага** внутри этого цикла, а не
новый API.

### 1.1 `deviceId` обязателен

Попытка принадлежит устройству. `authStatus` сверяет `deviceId`, и `ticket` выдаётся
только владельцу. Сессия (`UserDevice`) заводится на устройство, поэтому вход с
телефона не выкидывает из ноутбука.

### 1.2 Экран — функция последнего ответа сервера

Клиент **не решает шаг заранее**. Он не может: в момент клика по «Войти через MAX»
неизвестно, дойдёт ли пользователь до мессенджера; у другого провайдера того же
способа другая длина кода; `started → awaiting_user → done` — разные экраны одной
попытки. Единственный источник правды — `step` из последнего ответа.

`authStatus` не имеет побочных эффектов: его дёргают кэши, префетч и ретраи.
Отправка кода живёт в `authResend`.

## 2. Шаги

| `step.type` | что показать | что отправлять в `authSubmit` |
|---|---|---|
| `enter_phone` | поле телефона | номер |
| `enter_code` | ровно `step.codeLength` ячеек | код |
| `provider_dialog` | кнопку/QR из `step.clientPayload` | ничего, ждать |
| `redirect` | `window.location = step.redirectUrl` | ничего |
| `dial_number` | крупно `step.dialNumber` + кнопка `tel:` | ничего, ввода нет |
| `await_signal` | спиннер | ничего |

`step.id` — версия шага. Он перегенерируется при любой смене цели или способа, и
`authSubmit` со «вчерашним» `step.id` получает `failReason: stale_step` («обновите
экран»), а не «неверный код». Это защита от формы, оставленной во второй вкладке,
пока в первой сменили номер.

**Чего на экране быть не должно:** длины кода, взятой из константы (`step.codeLength`
— единственный источник; у flash-call это 4, у SMS 6), самодельной фразы «введите
последние N цифр» (`step.hint` приходит с сервера целиком и локализованным),
`dialNumber` до соответствующего шага.

### 2.1 Исходы

`failReason` различает то, что для пользователя означает разные действия:

| код | что случилось | что делать |
|---|---|---|
| `wrong_code` | не тот код, попытки остались | поле активно, показать `attemptsLeft` |
| `code_locked` | бюджет исчерпан, код уничтожен | «запросите новый» |
| `expired` | время вышло | повтор или другой способ |
| `stale_step` | экран устарел | перерисовать по свежему `authStatus` |
| `phone_mismatch` | в мессенджере привязан **другой** номер | сказать это прямо |
| `send_failed` | доставка не удалась | предложить другой способ |
| `rate_limited` | слишком часто для этого номера | таймер |

## 3. Выбор способа

`authMethods(purpose, login?)` возвращает два списка одним запросом:

- `identity` — кнопки входа. От номера не зависят, запрашиваются при загрузке страницы;
- `proof` — способы подтверждения для конкретного `login`. Зависят от самого номера
  (страна, оператор), поэтому запрашиваются по нажатию «Продолжить».

Плюс `phoneLoginAvailable`: если `false` — поле телефона не рисовать вообще.

Правила экрана:

- кнопка под полем телефона — нейтральное «Продолжить», не «Получить код по SMS»:
  что произойдёт дальше, знает только сервер;
- один доступный способ — экрана выбора нет, стартуем сразу;
- ноль — честная ошибка «вход по телефону сейчас недоступен», а не вид отправки;
- **«другой способ» — обязательный элемент.** Flash-call и дозвон отказывают молча и
  адресно (оператор режет короткие вызовы, стационарный номер, роуминг), при этом
  провайдер рапортует «вызов выполнен». Никакой серверный водопад тут не спасёт —
  спасает только `authSwitch`. Список доступных лежит в `availableMethods`.

Внутри одного способа сервер сам перебирает провайдеров, невидимо. Именно поэтому
экран обязан перерисовываться по ответу: у следующего провайдера может быть другая
длина кода.

## 4. Что где происходит

**Вход по телефону:**
```
authStart(purpose:"login", login:"79991234567", captcha)
  → step: enter_code(6), код уже отправлен
authSubmit(id, step.id, "123456") → done + ticket
authExchange(ticket) → JWT
```

**Вход через мессенджер:**
```
authStart(purpose:"login", method:"max")   → step: provider_dialog { deep-link, qr }
  поллинг authStatus…            пользователь поделился контактом в боте
  провайдер номер не дал         → step: enter_phone
  гейт включён                   → step: enter_code
  гейт выключен и номер доказан  → done сразу
```
Код уходит **лениво** — в момент, когда клиент впервые показал форму (первый рендер
дёргает `authResend`). Пользователь, дошедший до мессенджера и закрывший вкладку, SMS
не получает и денег не стоит.

**Подтверждение опасной операции:**
```
authStart(purpose:"verify:delete_account") → … → ticket → userDelete(ticket)
```
Код, выданный «для входа», удаление аккаунта не откроет: `purpose` проверяется при
погашении билета.

`login` для `verify:delete_account`, `verify:unlink_identity`, `verify:link_identity`
**игнорируется**: адресат берётся сервером — основной номер аккаунта. Иначе тикет
доказывал бы владение любым номером, который назвал клиент, а `consumeTicket` сверяет
`purpose` + `userId` (из JWT) + `deviceId` — всё то, что уже есть у того, кто увёл
сессию (review2 §1.2). Шага `enter_phone` для этих purpose не бывает; если у аккаунта
нет ни одного доказанного способа входа, `authStart` отвечает `no_incumbent`.
Если оператор разрешил такому purpose identity-метод (мессенджер), профиль принимается
только когда он **уже привязан** к этому же аккаунту и доказан.

`verify:phone` и `verify:phone_change` — наоборот, по определению про новый номер:
там `login` от клиента и есть предмет доказательства.

## 5. Личный кабинет

`myAccount` возвращает набор способов входа и **политику**:

- `identities[]` — что привязано, с маской (`+7 ••• 42-88`, `@va•••ya`), с `proofAt`
  (null = заявлено, но не доказано — номер из гостевого заказа, входа он не даёт);
- `policy` — `canAddPhone`, `canChangePhone`, `maxPhones`, свободные слоты по провайдерам,
  режим предупреждений и куда они уйдут.

`canUnlink` и `unlinkBlockedReason` считает **сервер**. Клиент не должен выводить их
сам из длины списка: он разойдётся с сервером на краях (окно защиты,
`ALLOW_USER_WITHOUT_PHONE`, недоказанная гостевая identity) и разойдётся молча —
кнопка есть, нажатие даёт ошибку.

Привязка — обычный `authStart(purpose:"link", method:…)`. Новых операций две:
`authUnlink(identityId, ticket)` и `authSetPrimaryPhone(identityId, ticket)`, обе
требуют билет свежей попытки соответствующего назначения.

**Любое изменение набора способов входа поднимает тревогу**: действующему владельцу
уходит SMS на номер, который был у него **до** изменения. Доставка одна — через пайплайн
уведомлений, правилами `user_identity_linked_sms`, `user_identity_unlinked_sms` и
`user_primary_phone_changed_sms`: они засеяны включёнными, `channelsMode: fixed`,
`fixedChannels: ["sms"]`, `important` — водопад каналов их не размывает. Прежний номер
приезжает снимком в `recipient.address`, потому что к моменту доставки `User.phone` —
уже проекция изменённого набора identity. Исключение одно — первая identity на свежем
аккаунте, это регистрация.
При `AUTH_LINK_NOTICE_POLICY=confirm` привязка вообще не завершается, пока владелец
не подтвердит её на своём номере: попытка отдаёт `failReason: confirm_required` и
билет, дальше `authLinkConfirm(linkTicket, confirmTicket)`.

## 6. Корзина только для вошедших

Настройка `REQUIRE_AUTH_FOR_CART` (boolean, по умолчанию выключена; тумблер в менеджере
настроек, применяется в рантайме без перезапуска). Включена — анонимный посетитель не
может ни завести корзину, ни положить в неё блюдо. Выключена или не задана — гостевая
корзина по `deviceId`, как всегда; миграций нет.

### 6.1 Как клиент об этом узнаёт

```
restrictions { requireAuthForCart }   # Boolean, никогда null
```

Читать **до** первого блюда и показывать экран входа сразу, а не после провалившейся
мутации. По ошибке распознать ситуацию нельзя: `formatError` отдаёт клиенту только
`message/locations/path`, `extensions` выбрасывается — кода ошибки нет, а текст сообщения
не контракт.

### 6.2 Что получает гость при включённом флаге

Гость — это запрос без JWT **или с протухшим**: оба случая одинаковы и оба ведут на экран
входа.

Флаг охраняет **не существование корзины, а то, что покупатель в неё кладёт**. Создание
строки заказа — это витрина просит `orderId`, с которым будет работать, и сервер сам её
наполняет (`ORDER_INIT_PRODUCT_ID`). Поэтому:

| запрос | результат |
|---|---|
| `order` без `orderId` | корзина создаётся, как и при выключенном флаге; init-продукт в ней есть |
| `orderAddDish`, `orderReplaceDish`, `orderRemoveDish`, `orderSetDishAmount` с неизвестным `orderId` | корзина создаётся, но само действие покупателя отклоняется |
| `orderAddDish` в уже существующую анонимную корзину | ошибка из ядра, корзина остаётся как была |
| `orderCheck` / оформление анонимной корзины | ошибка из ядра, `{ code: 20 }` (§6.4) |

Барьер стоит в ядре (`Order.addDish`, `Order.doCart`, `Order.check`), а не только в GraphQL,
поэтому его видят все интеграции. Позиции, которые кладёт сам сервер (промо,
`ORDER_INIT_PRODUCT_ID`), под него не попадают.

Клиент узнаёт об этом из `restrictions.requireAuthForCart` и показывает вход **до первого
блюда**, а не после провалившейся мутации: по ошибке ситуацию не распознать (§6.1).

### 6.3 Гостевая корзина при входе

Выдача JWT (`authExchange`) забирает в аккаунт анонимные корзины **этого `deviceId`** —
в состояниях `NEW`/`CART`, не оплаченные. Клиенту ничего делать не нужно: `orderId`,
который он держал до входа, остаётся рабочим. Это работает и при выключенном флаге —
раньше корзина, набранная до входа, оставалась ничьей.

Границы: только текущее устройство и только после того, как `issueToken` увидел, что оно
**сейчас** залогинено под этим аккаунтом; корзина, у которой уже есть владелец, не
переподвешивается; ошибка привязки вход не роняет. Если корзина всё же пришла анонимной
(набрана на другом устройстве) — запросить `order` без `orderId` и получить новую, уже
привязанную.

Проверка устройства доказывает меньше, чем кажется: `deviceId` приходит от клиента, а
`User.authDevice` перевешивает устройство на того, кто с ним вошёл последним. Поэтому
забираются только корзины, в которых **нечего забирать лично**: пустой `customer` — либо
телефон в `customer`, уже доказанный этим аккаунтом. `Order.check` пишет `customer`
(имя, телефон, адрес) ещё в состоянии `CART`, так что неуспешный чек оставляет корзину с
PII, и брать такую по одному лишь `deviceId` нельзя (review2 §4.5). Остальные остаются
на месте — теряется корзина, а не чужие персональные данные.

### 6.4 Оформление

Тот же флаг охраняет и выход: `Order.check` анонимной корзины без JWT отвечает
`{ code: 20, error: "authorization required" }`. Иначе инвариант «заказ только с
аккаунтом» держался бы лишь для корзин, набранных после включения флага — корзина,
набранная до него, интеграцией или на другом устройстве, доходила до оформления
(review2 §4.2).

## 7. Чего больше нет

Удалено без deprecated-обёрток — потребителей в этом репозитории не было:

| было | стало |
|---|---|
| `login(login, phone, password, otp, captcha)` | цикл `authStart`/`authSubmit`/`authExchange` |
| `OTPRequest(login, captcha)` | `authStart(purpose:"login", login)` |
| `startAuth` / `completeAuth` / `authStatus(stateId)` | `authStart` / `authStatus(id)` |
| `setAuthPhone` / `requestAuthOtp` / `resendAuthOtp` / `confirmAuthPhone` | `authSubmit` / `authResend` |
| `myAuthProviders` | `authMethods(purpose:"link")` + `myAccount` |
| `linkAuthProvider` / `unlinkAuthProvider` | `authStart(purpose:"link")` / `authUnlink` |
| `registration(login, phone, password, otp, …)` | `registration(firstName, …)` под JWT — только профиль |
| `restorePassword(login, phone, password, otp)` | удалено: пароля как способа входа в v2 нет (`.ai-notes/auth/remove-password.md`) |
| `userDelete(otp)` | `userDelete(ticket)` |
| `restrictions.user.OTPlength` | `step.codeLength` (поле осталось, но врёт по построению) |
| `restrictions.user.loginField` | `authMethods` (поле осталось, но всегда отвечает `'phone'`) |

Настройки `CORE_LOGIN_FIELD`, `LOGIN_OTP_REQUIRED`, `CORE_LOGIN_OTP_REQUIRED`,
`DEFAULT_OTP_ADAPTER`, `CREATE_USER_IF_NOT_EXIST` удалены вместе с кодом, который их
читал. `User.login` как колонки больше нет: ключ аккаунта — `User.id`, а всё, что
пускает внутрь, — это строка `AuthIdentity`.
